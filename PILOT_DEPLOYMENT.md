# Подготовка SAVEAT к пилоту

Production в ходе этой работы не изменялся. Проверки проведены локально.

## Окружение

- Backend: Python 3.14, `uv sync --locked`, PostgreSQL, `uv run alembic upgrade head`
  **на staging перед выкладкой**. Образец переменных: `backend/.env.example`.
- Задайте отдельный случайный `JWT_SECRET_KEY` (минимум 32 байта), защищённый
  PostgreSQL URL с TLS; прямое соединение или session pooler. Использование
  transaction pooler Supabase и его настройки prepared statements отдельно
  проверяются на staging; в этой работе подключений к Supabase не было.
- `CORS_ORIGINS` — JSON-массив точных HTTPS origins web-клиента. Wildcard
  отклоняется. Localhost остаётся доступен по умолчанию для разработки.
- Web: `npm ci`, `NEXT_PUBLIC_API_URL=https://<api-host>` **во время сборки**,
  `npm run build`, `npm start`. Используйте HTTPS reverse proxy с HSTS.
- Mobile: `npm ci`, `EXPO_PUBLIC_API_URL=https://<api-host>` во время сборки.
  Для Android Maps нужен `GOOGLE_MAPS_API_KEY`; для push — корректный EAS
  project ID и подписанный development/production build. Localhost и адрес
  Metro не подходят для установленного production-приложения.
- Не публикуйте dev-серверы Next/Expo. Настройте доверенные адреса прокси в
  Uvicorn; не доверяйте forwarded headers от произвольных клиентов.
- `/health` — liveness; `/health/database` — readiness (503 без деталей
  соединения при отказе БД). Логи reverse proxy не должны содержать Authorization.

## Порядок обновления

1. Сделать резервную копию и проверить восстановление на staging.
2. На staging выполнить три новые миграции до `83fd02a14b7c`.
3. Проверить `SELECT id FROM offers WHERE quantity_remaining < 0 OR
   quantity_remaining > quantity_total`. Новое CHECK-ограничение установлено
   как NOT VALID: новые некорректные записи запрещены, старые не переписываются.
   После отдельной проверки данных выполнить `ALTER TABLE offers VALIDATE
   CONSTRAINT ck_offers_stock_bounds` в согласованное окно обслуживания.
4. Выложить backend и оба обновлённых клиента. Старый checkout без ключа
   поддерживается, но не получает защиту от повторов. Старые push-подписки
   без сессии перестают отправлять push до повторной регистрации устройства.
5. Проверить checklist ниже, затем проводить production rollout отдельно.

Откат на staging: остановить обработчики и выполнить `uv run alembic downgrade
a91f37c4e6b2`, затем вернуть совместимые версии приложения. Это удаляет только
новые поля и служебные таблицы; заказы, позиции, остатки и legacy-поля остаются.
Откат теряет ключи повторов, журнал отозванных JWT и очередь push. Поэтому при
реальном откате нужны остановка записей и ротация JWT-секрета, чтобы ранее
отозванные токены не стали действительными. Копию очереди/идемпотентных ключей
нужно сохранить отдельно. Production-откат здесь не выполнялся.

## Проверка нового заведения

Оба пути регистрации создают `pending`; действующие аккаунты и demo seed
остаются `active`. Владелец может войти и увидеть ожидание проверки, но
не публиковать предложения и не управлять заказами.

Оператор SAVEAT проверяет контакт, право представлять пекарню и её адрес,
затем с доверенной машины и с нужным окружением выполняет:

```text
cd backend
uv run python -m app.approve_business <business-uuid> --expected-name "Точное название"
```

Команда сверяет UUID, название и `pending`, блокирует строку и атомарно
меняет статус на `active`. Публичного admin endpoint нет. Доступ к окружению
БД является административным доступом. Для отдельного закрытого demo-окружения
можно явно задать `BUSINESS_REGISTRATION_REQUIRES_APPROVAL=false`; для пилота
оставьте `true`. Массовой активации существующих pending-бизнесов нет.

## Push и сессии

При `PUSH_WORKER_ENABLED=true` API запускает poller очереди. Если worker
вынесен в отдельный процесс, задайте API `PUSH_WORKER_ENABLED=false` и
запустите `uv run python -m app.push_worker` под менеджером процессов.
SKIP LOCKED разрешает несколько workers; сеть не входит в checkout.

Очередь хранит доставки на конкретную подписку/пользователя/сессию. Перед
отправкой владение проверяется снова. Внешний push содержит только общее
«У вас новое уведомление» без имени, кода, адреса или order ID; полный текст
остаётся в авторизованном списке уведомлений. Это намеренное изменение для
общих устройств и offline logout. Уведомления, уже принятые ОС, нельзя отозвать
с сервера. Клиенты очищают показанные уведомления при выходе.

Повторы временных ошибок: до 8 попыток, задержка от 60 секунд до часа.
`last_error` и `attempts` сохраняются; отслеживайте завершённые записи с
ошибками и рост незавершённой очереди. Web 404/410 и Expo ticket
DeviceNotRegistered удаляют нерабочую подписку. При потере процесса между
приёмом push провайдером и commit возможен повтор; web tag использует ID
уведомления. Exactly-once и конечная доставка на устройство не гарантируются.
Получение последующих Expo delivery receipts пока не реализовано.

Не расширяйте `WEB_PUSH_ALLOWED_HOSTS` внутренними/непроверенными адресами.
Список точных hostnames содержит FCM, Mozilla и Apple; редиректы запрещены.
Иные легитимные провайдеры требуют отдельного добавления hostname и проверки.

## Безопасность web-auth

Web пока использует bearer JWT в localStorage. Cookies не вводились:
текущие страницы обращаются к API напрямую, а web/API deployment origins
не закреплены. Частичная замена хранилища сломала бы существующие запросы.
Для перехода: выбрать same-origin BFF или согласованную cookie domain policy,
перевести все web-запросы на HttpOnly/Secure/SameSite cookie, добавить проверку
Origin и CSRF-токен для изменяющих запросов, реализовать совместимый logout и
проверить multi-tab/account switching. Mobile продолжает использовать bearer
JWT в SecureStore. XSS-риск localStorage остаётся открытым пунктом аудита.

Вход ограничен 10 попытками на email и 60 на IP за 10 минут; регистрация —
5 на email и 10 на IP в час. Оба auth-router используют общие атомарные
PostgreSQL-счётчики; успешные попытки тоже учитываются. Ответ 429 содержит
Retry-After. Ключи счётчиков хешированы с секретом; пароль/email в них не хранятся.

## Ручной QA — NOT TESTED на устройстве

- На двух реальных устройствах: A бронирует последнюю штуку, B получает
  отказ, видит «Нет в наличии», сохраняет корзину, может удалить позицию.
- Повторить с paused/expired/removed, пустой витриной, частичным остатком,
  новой ценой, режимом без сети и возвратом в корзину.
- Оборвать ответ checkout после commit, повторить попытку с тем же ключом;
  убедиться, что в истории один заказ. После перезапуска приложения проверить
  сохранение ключа; после изменения состава — новый ключ.
- A включает web/Expo push, выходит; B входит на том же устройстве.
  Создать уведомления A и B, проверить получателя и отсутствие частных данных.
  Повторить с истёкшим JWT, offline logout и запрещёнными разрешениями push.
- Проверить push при закрытом приложении, перезапуске backend, временном
  отказе провайдера, на Android и iOS подписанных сборках.
- Клиент получает код/QR, сотрудник сканирует его, выдаёт заказ, клиент
  обновляет статус. Повторить неверный/чужой/отменённый/уже выданный код и
  потерю ответа. Проверка окон выдачи сохраняет прежнее правило: API не
  запрещает выдачу после pickup_end. Изменение этого правила требует решения продукта.
- Зарегистрировать новый бизнес, проверить ожидание, одобрить через CLI,
  обновить статус; проверить существующий demo и staff/manager/owner.
- Проверить HTTPS, approved origins, камеру/карты, разрешения, cold start,
  shared-device logout и expiry в staging.
